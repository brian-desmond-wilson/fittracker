# Catalog Enrichment Pipeline — Design Spec

**Date:** 2026-09-11
**Status:** Approved design, not yet planned
**Surface:** Exercise creation (match review → `mobile/src/components/training/crossfit/CatalogItemWizard.tsx` → `createCatalogExercise` in `mobile/src/lib/supabase/frontDoor.ts`), a new edge function `supabase/functions/enrich-exercise`, and the exercise page's overflow menu and Demo Video section.
**Companion spec:** `docs/superpowers/specs/2026-09-11-exercise-detail-page-v2-design.md` renders what this pipeline fills.

## 1. Problem

Of 290 catalog rows, 204 have no description, 262 no demo video and 197 no image. The capture extraction already returns a description, muscles, equipment and skill level for every exercise it finds, and the "Create new" path throws all of it away, prefilling the wizard with the name alone. Images are generated by two different edge functions with two prompt owners and two storage buckets. Nothing fills a gap after the fact, so every gap becomes a future backfill.

## 2. Goals / non-goals

**Goals**
- A new exercise gets its description, demo video and image without anyone doing anything after saving the wizard.
- Creation carries the capture extraction through to the wizard so the human reviews real values instead of blanks.
- One idempotent, fill-only enrichment job; one image generator; one bucket.
- One backfill for descriptions and videos, run once, then never needed again because a periodic sweep keeps the catalog whole.
- Human edits always win over machine fills, forever.
- A way to override any exercise's demo video with a clean one at any time.

**Non-goals**
- No image backfill for the 197 rows missing one (decision 5).
- No invented video links: a row with no single-exercise capture keeps an empty video until a human sets one (decision 2).
- No re-describing rows that already have text.
- No change to the capture-post extraction prompt or model.
- No database queue, trigger or cron (decision 4).

## 3. Decisions (user-approved 2026-09-11)

1. **Two specs.** The page and the pipeline are planned and built separately.
2. **Default demo video is the captured post** when the post was captured as a single exercise. Exercises born from a workout post get none by default.
3. **Override at any time.** The wizard's existing video field is the override; a "Find a demo" action on the page opens a YouTube search for the name. The pipeline fills only an empty slot, so a human-set video is never replaced.
4. **One edge function called from the phone after creation**, with a `sweep` mode for the backfill and for periodic self-healing. Chosen over a trigger + queue and over enriching inside capture-post.
5. **Images join the pipeline; images stay out of the backfill.** New rows get an image from the same job. The one-time sweep runs with images off.

## 4. Experience

**Creating from a match review.** "Create new" opens the wizard prefilled with the extraction's name, description, primary and secondary muscles, equipment and skill level for that name. The reviewer edits and saves as today. The extraction is read from the source's stored raw extraction, matched by the reviewed name.

**After any wizard save** (create, from a review or standalone) the phone fires `enrich` for the new id in the background and returns to what it was doing. Nothing waits on it. If the reviewer comes back to the page within a few seconds the sections fill in on next open.

**On the page.**
- Overflow menu: "Enrich" (runs `enrich` for this row and reloads) and "Regenerate image" (forces a new image, the only path that overwrites an existing one). The page's own client-side prompt builder is deleted; the server owns the prompt.
- Demo Video section: preview card plus "Find a demo ›", per the page spec §4.7. To set the found video, open Edit and paste the URL into the video field.

**Backfill.** Run once from a terminal: `sweep` with images off, dry-run first to report counts, then for real. Reported as a one-line summary of filled fields.

**Periodic sweep.** The Training tab, on open, runs `sweep` with images on and a batch cap of 20 at most once every 7 days per device, recorded in AsyncStorage. Only an admin profile's device runs it (the `sweep` action is admin-gated, §6); other users' devices skip the check entirely. This is what makes "never backfill again" true without database infrastructure: `pg_net` was removed from the project in the baseline, so a server-side schedule would mean re-enabling it, and a few rows a week does not justify that.

## 5. Fill rules

A field is **fillable** when it is null or blank and its provenance is not `user`.

| Field | Source, in order | Written when |
|---|---|---|
| `description` | 1. The capture extraction's description for this exercise, when the row was created from a review and the source's raw extraction has it. 2. Generated: the capture-post model, action `describe`, given name, aliases, category, muscles, equipment and skill level. | Fillable and the text passes validation (§8). |
| `video_url` | The `source_url` of the most recent reviewed `captured_sources` row linked through `source_exercises` whose capture produced no `captured_workouts` row (a single-exercise capture). | Fillable and such a source exists. |
| `image_url` | The server-side generator (`generate-exercise-image`'s logic), prompt built from name, description, equipment and discipline, stored in the `exercise-images` bucket. | Fillable and images are enabled for this run. |

**Provenance.** A new column `exercises.enrichment jsonb NOT NULL DEFAULT '{}'`, keyed by field: `{"description": {"by": "extraction" | "model" | "user", "at": "<iso>"}, "video_url": {"by": "capture" | "user", ...}, "image_url": {"by": "model" | "user", ...}}`. The wizard's update path sets `by: "user"` for any of the three fields it changes to a non-empty value, and clears the key when it blanks a field (blank means "fill this again"). The pipeline sets `by` to its source. `Regenerate image` writes `by: "model"` and is the only overwrite.

**Bucket unification.** `generate-movement-image` is deleted. Existing `image_url` values pointing at `movement-images` keep working (the bucket stays, read-only); new images go to `exercise-images`.

## 6. Architecture

**New**

| File | Responsibility |
|---|---|
| `supabase/functions/enrich-exercise/index.ts` | Actions: `enrich {exerciseId, images?: boolean, force_image?: boolean}` → fills per §5, returns `{filled: string[], skipped: Record<string,string>}`; `sweep {images: boolean, limit: number, dryRun: boolean}` → selects rows with any fillable field, calls the enrich logic per row, returns counts. Service-role inside; caller must be an authenticated user for `enrich`, and `sweep` requires the caller to be an admin profile. |
| `supabase/functions/enrich-exercise/fill.ts` | Pure decision logic: given the row, its provenance, its candidate sources and the run flags, return which fields to fill and from where. No I/O. Unit-tested with Deno test. |
| `supabase/functions/capture-post` action `describe` | Small prompt returning `{description}` for one exercise from its structured facts. Same model and client as the other actions. |
| `supabase/migrations/20260918130000_exercise_enrichment.sql` | Adds `enrichment jsonb`; seeds `by: "user"` for every row whose `description`, `video_url` or `image_url` is already set, so the backfill cannot touch anything that exists today. |
| `mobile/src/lib/supabase/enrich.ts` | `enrichExerciseInBackground(id)`, `runEnrichSweep(opts)`, and the 7-day gate for the periodic sweep. |
| `mobile/src/lib/extractionPrefill.ts` | Pure: from a source's raw extraction and a reviewed name, produce the wizard's initial values (description, muscles, equipment, skill level) or nothing when the name is not in the extraction. |
| `scripts/enrich-backfill.ts` | Calls `sweep` with `images: false`, `dryRun` first; prints the summary. |

**Changed**

| Was | Becomes | Change |
|---|---|---|
| `MatchReviewSheet.tsx` "Create new" passes `initialName` | Passes the extraction prefill | Reads the source's raw extraction through `extractionPrefill`. |
| `CatalogItemWizard.tsx` fires `generateExerciseImageInBackground` after create | Fires `enrichExerciseInBackground` | One call replaces the image-only call. |
| `frontDoor.ts` update path writes the three fields | Also writes `enrichment` provenance for them per §5 | Same statement, one more column. |
| `TrainingItemDetailScreen.tsx` builds an image prompt on the phone and calls `generate-movement-image` | Menu items "Enrich" and "Regenerate image" both call `enrich-exercise` | Client prompt code deleted. |
| `mobile/src/lib/supabase/exerciseImages.ts` | Thin wrapper over `enrich` with `force_image` | Keeps its two callers compiling. |
| `supabase/functions/generate-movement-image` | Deleted | Its logic already exists server-side in `generate-exercise-image`, which the new function imports. |

## 7. State and persistence

- Provenance is the only new persistent state, on the exercise row.
- The periodic sweep gate is a per-device timestamp in AsyncStorage, key `catalog.enrichSweep.lastRun.v1`.
- `enrich` is idempotent: running it twice on a full row fills nothing.

## 8. Error handling

- Enrichment never blocks or fails creation. Any error inside `enrich` is caught per field; the field stays empty and the next sweep retries it.
- Description validation: 40–600 characters, plain text, must not start with the name of a different catalog exercise (case-insensitive match against all names and aliases). A rejected text is not written and the reason goes in `skipped`.
- Video: only `instagram.com` and `tiktok.com` URLs from stored sources are ever written by the pipeline; the human field accepts any `https://` URL.
- Image generation failures are logged and skipped, as today.
- `sweep` stops at `limit` rows and reports how many remain, so a backfill is resumable and the weekly run is bounded.

## 9. Testing

- Deno unit tests on `fill.ts`: fillable vs user-provenance, extraction-before-model, single-exercise-capture detection, images flag, force_image overwrite, validation rejects.
- Unit tests on `extractionPrefill.ts`: name present, absent, case and spacing differences.
- Dry-run sweep against the live database before the real backfill; the two counts are recorded in the plan.
- Device walk: capture a single-exercise post, create it from the review, confirm the page shows description, the post as video, and an image within a minute; set a manual video, run Enrich, confirm it is untouched.

## 10. Out of scope

Image backfill; a server-side schedule; YouTube API lookups; re-extraction of old captures; editing descriptions on the page (still the wizard).
