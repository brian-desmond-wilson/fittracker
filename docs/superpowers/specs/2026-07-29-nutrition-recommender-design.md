# Nutrition OS — Phase 3: Recommender + "Eat Next"

**Date:** 2026-07-29
**Status:** Approved design, pending implementation plan
**Branch:** `nutrition-os/recommender` (based on `nutrition-os/meal-library` @ `b8f89ac`)
**Companion docs:** Phase 1 spec `2026-07-28-nutrition-preference-model-design.md` (live in prod), Phase 2 spec `2026-07-29-nutrition-meal-library-design.md` (executing concurrently — see §11), *FitTracker — Software Architecture Reference* / *Concept Map* (snapshot 2026-07-28).

## 1. Context

Phase 3 turns the Phase 1 preference model and Phase 2 Meal Library into the thing Brian actually asked for: the app telling him what to eat and when. Per the Phase 1 spec's design stance, **the recommender is a filter, not a parser** — deterministic, explainable, offline, pure TypeScript. An LLM layer is a later, separate concern.

## 2. Goals

- One pure engine (`eatNext.ts`) producing ranked meal recommendations **with reason strings generated by the same predicates that did the ranking**, plus a nudge decision.
- Four surfaces: Home "Eat Next" card, in-Meals "Suggested now" row, ramp advance banner promoted to Home, and a pace-aware "eat nudge" notification family.
- Resolve the standing aggregation duplication: **client math wins; the dead `daily_nutrition_summary` / `daily_water_summary` views are dropped** (audit D6, Concept Map §18.2).
- Fix the notification-eviction landmine so all reminder families survive a Schedule-screen reschedule.
- Training awareness: **post-workout window only** — grounded in `workout_instances` completed today (the water-bonus precedent). No forward-guessing.
- Add the missing `mealPace.ts` Jest suite (audit R2 designated target) since the engine leans on it.

## 3. Non-goals (later phases / explicitly out)

Assemblable-now filtering and expiration awareness (Phase 4); shopping/vendor logic (Phase 5); LLM/natural-language recommendations; pre-workout inference (the program cursor is not date-aware — it would fire on rest days); multi-nudge scheduling; any new server-side logic; changes to how meals are logged (Phase 2 owns that flow).

## 4. Decisions log

| Decision | Choice | Why |
|---|---|---|
| Engine placement | Pure client lib + one assembly hook | Matches `rampProgress`/`mealScore`; Jest-testable; offline; one truth for all surfaces |
| Aggregation | Client math; drop both views | Views are unconsumed and stale (no sodium/fiber); client path is live and complete; forced pick-one rule |
| Training signal | Completed-today workouts only, 3 h window | Only deterministic oracle available; mirrors `water_workout_bonus_oz` precedent |
| Nudges | Pace-aware resync, single pending slot, opt-in | Local notifications fire blind — only app-active recompute can be honest; static reminders already exist |
| Nudge setting home | `profiles.eat_nudges_enabled` (default false) | Kernel rule: per-user setting = profile attribute (water/meal reminder precedent) |
| Landmine fix scope | Tag schedule-event notifications; family-scoped cancel | Fixes eviction for every family, not just ours; smallest correct change |
| Reason strings | Assembled from ranking predicates inside the engine | UI can never claim a reason the ranking didn't use |

## 5. The engine — `src/lib/eatNext.ts`

Pure, no I/O, options-object API, exported policy constants (the `rampProgress` mold).

### 5.1 Input

```
EatNextInput {
  nowMinutes: number                       // minutes since midnight, local
  windowStartMinutes / windowEndMinutes    // from profiles.water_window_* (shared waking window)
  mealTimesMinutes: { breakfast, lunch, dinner }
  dayTotals: MacroTotals                   // sumNutrition over today's meal_logs
  goals: MacroGoals
  caloriePace / proteinPace: MealPaceState // from computeMealPace — passed in, never recomputed
  meals: Array<{ meal: MealWithItems; totals: MealTotals; score: BrianScoreResult }>
  maxPrepMinutes: number                   // nutrition_constraints.max_prep_minutes
  workoutCompletedAtMinutes: number | null // latest completed workout today, local
  nudgesEnabled: boolean
}
```

### 5.2 Output

```
EatNextResult {
  context: "goal_hit" | "post_workout" | "emergency" | "catch_up" | "next_meal" | "after_window"
  message: string | null                   // context-level line ("Target hit — nothing needed.")
  recommendations: Array<{ mealId: string; reasons: string[] }>   // top 3
  nudge: { fireAtMinutes: number; title: string; body: string } | null
}
```

### 5.3 Context detection — first match wins

1. **`after_window`** — past `windowEndMinutes`: no recommendations, no nudge.
2. **`goal_hit`** — calories ≥ goal: no meal recommendations. Exception: if protein is still ≥15 g short, recommend the single highest-protein `bridge`/`calorie_booster` meal under 300 cal with reason "protein short"; if no such meal exists, the context stays terminal with its message (it does not fall through to other contexts).
3. **`post_workout`** — `workoutCompletedAtMinutes` within the last 180 min: candidates are role=`post_workout` first, then any meal with ≥25 g protein; protein language leads the reasons.
4. **`emergency`** — now past `dinner` time AND calorie pace `behind` with `catchUpAmount ≥ 400`: candidates from category=`emergency` plus roles `emergency_catchup`/`calorie_booster`, sorted calories-**descending** (biggest rescue first).
5. **`catch_up`** — calorie pace `behind`: candidates whose total calories fall within ±35% of `catchUpAmount`; small gaps naturally surface `bridge` meals.
6. **`next_meal`** (default; covers `on_pace`, `ahead`, `before_window`) — next slot = earliest of breakfast/lunch/dinner strictly after now (else `snack`); candidates are meals whose category maps to that slot (`shake` maps to `snack` slot, `emergency` never surfaces here); if ≥120 min remain before the next meal time, prefer role=`bridge`/category=`snack`.

**Fall-through rule:** a context with zero surviving candidates falls through to the next context (never a blank result while candidates exist anywhere). `after_window` and `goal_hit` (calorie branch) do not fall through — they are terminal by design.

### 5.4 Hard filters (inside every context)

- `containsNever` meals never surface, in any context.
- `prep_minutes > maxPrepMinutes × 2` never surfaces. Meals in `(maxPrepMinutes, maxPrepMinutes × 2]` may surface with an explicit reason "over your prep budget".

### 5.5 Ranking

Within the context's candidate set: role-match (context's preferred roles first) → **Brian Score `raw` descending** (the un-renormalized component sum — per Phase 2's banding finding the rounded /100 score barely discriminates; UI surfaces still display `score`/100) → `prep_minutes` ascending → name ascending. Fully deterministic: same input, same order, always. Top 3 returned.

### 5.6 Nudge decision

If `nudgesEnabled` AND calorie pace `behind` AND `catchUpAmount ≥ 250`: fire at **the next meal time after now, plus 20 min**; when no meal time remains, fire at **`windowEnd − 90 min`** instead — that is the fire time itself, with no further offset applied (the emergency check). *(Clarified 2026-07-29 during Task 2 execution: the original sentence's phrasing left it arguable that `+ 20 min` also applied to the `windowEnd − 90` case, yielding `windowEnd − 70`. It does not — `EMERGENCY_CHECK_BEFORE_END_MIN = 90` names the offset from window close, and the implementation was ruled correct.)* `fireAtMinutes` must be strictly after `nowMinutes`: if the computed time is already past, use `now + 20 min`; if even that exceeds `windowEnd`, the nudge is `null`. Title/body carry the gap and the top recommendation ("~650 cal to go — Korean Beef Bowl fixes it in 5 min") — "top recommendation" means the top recommendation *for closing the gap*, ranked by the nudge's own catch-up-band pass, which is deliberately independent of the context the UI surfaces at decision time (see §5.6 rationale in `eatNext.ts`). Otherwise `nudge: null` (the service treats null as cancel). At most one pending nudge exists, ever.

### 5.7 Policy constants (exported, tested)

`POST_WORKOUT_WINDOW_MIN = 180` · `EMERGENCY_MIN_GAP_CAL = 400` · `CATCH_UP_BAND = 0.35` · `NUDGE_MIN_GAP_CAL = 250` · `NUDGE_MILESTONE_OFFSET_MIN = 20` · `EMERGENCY_CHECK_BEFORE_END_MIN = 90` · `PROTEIN_SHORT_G = 15` · `POST_WORKOUT_MIN_PROTEIN_G = 25` · `BRIDGE_PREFER_GAP_MIN = 120` · `PREP_HARD_CAP_FACTOR = 2`.

## 6. Data assembly — `src/hooks/useEatNext.ts`

One hook returning `{ result: EatNextResult | null, loading, error, refetch }`. Parallel fetches: `fetchMealLibrary()` (Phase 2), today's `meal_logs` → `sumNutrition`, profile columns (`target_*`, meal times, water window, `eat_nudges_enabled`), `nutrition_constraints`, and today's completed `workout_instances` (`status = 'completed'` AND `completed_at` within today's **local** day, latest `completed_at`). *(Amended 2026-07-29 during Task 5 execution, ruled by the coordinator: this originally read `scheduled_date = today AND status = 'completed'`, which is a defective expression of §2's "workouts completed today". "Save Progress" leaves an instance `in_progress`/`partial`, `getTodaysWorkout` resumes the latest incomplete instance regardless of its `scheduled_date`, and finishing it stamps `completed_at = now` on a row still dated an earlier day — so a `scheduled_date` filter silently misses a workout finished minutes ago. Keying off `completed_at` in the local-day range also removes the need for a same-day guard in the hook.)* Computes `computeBrianScore` per meal and `computeMealPace` for calories/protein, then calls `recommendEatNext`. All surfaces and the nudge resync consume this hook — no surface computes independently.

## 7. Surfaces

### 7.1 Home "Eat Next" card — `src/components/EatNextHomeCard.tsx`

Full-width card between Today's Workout and Today's Summary, own section title ("Eat Next"), following the `TodaysWorkoutCard` pattern: self-fetching, `refreshKey` prop, `useFocusEffect` reload, loading / error+retry / empty states. Shows the top recommendation: name, first reason line, cal · protein · prep, score chip; red accent when context=`emergency`. `goal_hit`/`after_window` render the context message (never a blank card); empty library renders a "build your Meal Library" CTA into Track→Meals. Tap → `router.push({ pathname: "/(tabs)/track/meals", params: { suggestMealId } })`; the Meals screen reads the param and opens the Meal Library modal at that meal's detail (the Phase 2 `MealLibraryModal` gains an optional `initialMealId` prop; the param is consumed once and cleared).

The card triggers the nudge resync after each load (§8).

### 7.2 In-Meals "Suggested now" row — `src/components/track/meals/EatNextRow.tsx`

Slim strip rendered directly under `MealsPaceLines` (today view only, same `viewingToday` guard): top 2 recommendations as tappable chips ("Korean Beef Bowl · 450 cal behind"); tap opens the library modal at that detail. Refreshed by the screen's existing write-refetch path, so logging a meal immediately updates or clears the suggestion.

### 7.3 Ramp banner — `src/components/RampHomeBanner.tsx`

Above the Today's Workout section, rendered only when `assessRampProgress` (Phase 1 fetch + math, reused verbatim) returns `advance` and a next level exists. Text "Ready for Level N — {name}"; tap → `router.push("/(tabs)/profile?modal=nutrition")`; `app/(tabs)/profile.tsx` reads the `modal` search param on focus and auto-opens the Nutrition Preferences modal, then clears the param. The banner never writes — confirmation remains solely in the existing RampCard. Top-of-ramp (`advance` with no next level) stays a Preferences-only banner (Home shows nothing).

## 8. Nudge service + landmine fix

### 8.1 `src/services/eatNudgeService.ts`

New family, `data: { type: "eat-nudge" }`, modeled line-for-line on `mealReminderService`: `cancelAllEatNudges()` cancels only its tagged ids; `syncEatNudge(decision: EatNextResult["nudge"])` = cancel family → if decision non-null and permissions granted, schedule one one-shot DATE trigger at `fireAtMinutes` (today, local). Resync points: `EatNextHomeCard` after every load (covers app open/foreground), and MealsScreen after every meal-log write. Budget: ≤1 pending slot of the 64.

*(Amended 2026-07-29 during Task 6 execution, ruled by the coordinator: the two signatures above are stale — recorded here because Tasks 8 and 10 read this section for the resync contract, and a signature missing a required parameter is exactly the kind of gap that produces a compiling call that's wrong. `syncEatNudge`'s actual signature is `syncEatNudge(decision: EatNextResult["nudge"], sourceDay: Date)`, with `sourceDay` required, not optional. "at `fireAtMinutes` (today, local)" above now means "at `fireAtMinutes` on `sourceDay`, which callers must confirm is `now`'s local calendar day" — `fireAtMinutes` is minutes since local midnight on the day the decision was computed (§5.6, `EatNextNudge.fireAtMinutes`'s doc comment in `eatNext.ts`), not "whatever day it happens to be when `syncEatNudge` runs". A caller must pass `useEatNext`'s `computedAt` (§6) here, never a fresh `new Date()` read at call time — the latter is exactly the cross-midnight mis-schedule this parameter exists to close (decision computed shortly before local midnight, `syncEatNudge` invoked shortly after: the reconstructed fire time can land up to ~24h later than intended, silently). The actual resolution is done by a pure `nudgeFireDate(fireAtMinutes, sourceDay, now)` in `eatNext.ts`, co-located with the `EatNextNudge` contract it resolves, not by local `Date` arithmetic in the service. Separately, `cancelAllEatNudges()` returns `Promise<boolean>`, not `void`: a cancel that fails (the underlying expo-notifications calls threw) must not be followed by a schedule, or the ≤1-slot budget stated above breaks by a second route — `syncEatNudge` checks this return and skips scheduling when it's `false`, at the cost of a missed resync (recoverable at the next one) rather than a second pending nudge. Both changes ship in `mobile/src/services/eatNudgeService.ts` and `mobile/src/lib/eatNext.ts`; full reasoning and mutation-testing evidence in the Task 6 execution amendment.)*

### 8.2 Settings

`profiles.eat_nudges_enabled boolean not null default false` (migration, §9). Toggle added to the existing Notifications screen alongside meal reminders, with the standard test-fire button. Disabled → `syncEatNudge` only cancels.

### 8.3 Landmine fix (existing-behavior change, deliberate)

Event notifications already carry `data: { type: 'event_reminder' }` tags (verified 2026-07-29 — no new tagging needed). The fix is confined to `rescheduleAllNotifications`: replace its `cancelAllNotifications()` call with a family-scoped cancel (enumerate + cancel only `event_reminder` ids). The global `cancelAllNotifications()` remains available only for sign-out flows. This makes every reminder family (water, meal, weight, eat-nudge) survive a Schedule-screen reschedule — the same contract those families already honor toward each other.

*(Amended 2026-07-29 during Task 7 execution, ruled by the coordinator: "remains available only for sign-out flows" described an intent, not an existing call site. Verified during execution — `cancelAllNotifications` had **exactly one** caller in the entire app, the line inside `rescheduleAllNotifications` that this task replaced, so post-fix it has **zero** callers. It is kept exported anyway, but not on the plan's stated grounds: the sign-out flow that should call it doesn't. Two independent reviews confirmed that `app/(tabs)/profile.tsx:132-149` tears down SecureStore keys, calls `supabase.auth.signOut()`, and routes away without cancelling any notification, and that `app/_layout.tsx:35-40`'s `onAuthStateChange` listener only calls `setSession`. **A signed-out user therefore keeps receiving reminders from all five families indefinitely, and a second user signing in on that device inherits the previous user's reminders** — built from their water window, meal times, weight schedule, and calorie pace. That is a pre-existing correctness bug with a privacy edge, independent of Phase 3 and out of its scope (`profile.tsx` and auth teardown are not Phase 3 files); it was filed as its own task rather than fixed here, and `cancelAllNotifications` is retained as the correct primitive for it. Phase 3 sharpens the gap without causing it: eat-nudge becomes the fifth family that now correctly survives a reschedule, and will therefore also correctly survive sign-out.)*
